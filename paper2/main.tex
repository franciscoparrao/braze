\begin{abstract}
% Recortado a ~250 palabras el 2026-11-26 (antes 390): Springer suele pedir
% 150-250 y los abstracts EMSE de la muestra del vault miden 228-288.
Coding agents built on small, locally hosted language models fail more
often than frontier models. A tempting fix is to inject a reusable
playbook distilled from a stronger model's rescues. Such a playbook is
an instruction artifact re-sent on every round, so its cost grows with
the trajectory it is meant to shorten. We state this as an \emph{amortization condition},
used as a reporting convention: an injected section pays only if the
rounds it saves outweigh its per-round overhead. We test it in two
studies on a 20B mixture-of-experts executor and a pre-registered
replication on a dense 9B executor; confirmatory weight rests on the
replication and on a pre-registered re-run of the second study. Per-task break-even is $0.73$--$1.74$ rounds. On the 20B
executor a human-written playbook saves $0.95$ rounds on one of three
tasks (95\% CI $0.25$--$1.65$, which contains its break-even) and costs
net tokens on the other two. On the 9B executor it lengthens
trajectories by up to $1.75$ rounds, adds $2.7$k--$6.6$k net input
tokens per task, and lowers the pre-registered pass rate on one task
($10/20$ to $2/20$, Holm $p=0.041$). In the second study, which injects
the files touched in earlier sessions, a first run with the arms in
sequence showed a significant gain that a \emph{same-prompt control}
arm nearly matched; interleaving the arms removed this artifact, and
the memory then had no detectable effect ($-7$ of 102 cells, Holm
$p=0.59$). These positions are specific to short compile-repair tasks
and these executors; there, injected memory would pay only if its cost
dropped or it unlocked tasks the model otherwise fails.
\keywords{agentic coding \and instruction artifacts \and procedural
memory \and small language models \and negative results \and
pre-registration \and same-prompt control}
\end{abstract}

\section{Introduction}\label{sec:intro}
% Fuente: outline § "El giro" + § "Por qué un nulo es publicable".

Coding agents that run on small, locally hosted language models are
increasingly practical: free to run, private by construction, and fast
enough on commodity hardware to be useful
\citep{lu2024smalllm,corradini2025}. They also fail more often than
their frontier counterparts, which makes one idea for improving them
especially attractive. When the local model fails and a stronger cloud
model rescues it, distill the tutor's intervention into a reusable
procedural playbook (\emph{procedural memory}) and inject it into
future related tasks: the escalation is paid once and amortized
forever after. Variants of this idea circulate widely in the agent
literature as skill libraries, stored reflections, and memory
subsystems (Section~\ref{sec:related}). It sounds obviously good, and
it is exactly the kind of plausible technique that gets adopted
without measurement.
% NUEVO (PROMPT-SE, 2026-11-06) — revisar con el autor:
Viewed as a prompt-engineering decision, such a playbook is an
instruction artifact, in the same family as a system prompt or a
project rules file: the harness re-sends it to the model on every round,
so its cost grows with the length of the trajectory it is meant to
shorten. It is also a concrete engineering decision ---
whether a coding-agent harness should carry a distilled memory into
every session --- of the kind the emerging practice of \emph{harness
engineering} (Section~\ref{sec:related}) must make, today without a
measured criterion to guide it. What follows is that criterion and the
measurement behind it.

This paper measures it. In the regime we measured, it does not pay,
and the reason is structural. An agentic loop re-sends the
growing conversation to the model on every round, so a memory section
of $c$ tokens does not cost $c$ tokens per task: it costs $c \times
R$, where $R$ is the number of rounds the turn takes. Its benefit,
meanwhile, arrives only as \emph{rounds saved}. Balancing the two
yields an explicit amortization condition
(Section~\ref{sec:model}): in the configurations measured here, an
injected memory must eliminate between three quarters of a round and
nearly two rounds of interaction, depending on task and executor, to
break even.

We report two evaluations of prompt-injected procedural memory on
\braze{}, a local-first agentic coding harness, with a 20B-parameter
local executor, and a pre-registered replication of the first. Study~1
instantiates a multi-session benchmark (session A produces a
playbook, same-family tasks B measure transfer, a holdout H prices
misapplication) with a \emph{human-written} playbook, a strong a-priori condition for
content quality, across three compile-repair tasks (140 runs). Study~2 evaluates the production form of the same
idea, a project-memory hook that injects the files touched by previous
sessions, in a three-arm A/B whose middle arm is a \emph{same-prompt
control}: its prompt is byte-identical to the baseline by construction.
Study~2 ran twice, 306 runs each: first with the arms in sequence, and
then, after that run exposed an artifact, with the arms interleaved
under a new pre-registration. A pre-registered replication of Study~1
on a second, dense 9B executor (140 further runs) tests whether the
pattern is specific to one architecture. The confirmatory weight of
this paper rests on the replication and on the interleaved run of
Study~2, whose pre-registration order is verifiable against the public
repository; Study~1's pilot, whose order is not, we report as
exploratory (Section~\ref{sec:method-prereg}).

Both studies land on the same side of the frontier, though they probe
different points of it: Study~1 (exploratory) prices content-rich
memory, Study~2 (confirmatory) a content-thin one. On the 20B executor
the playbook saves $0.95$ rounds on one task, a point estimate above
that task's break-even of $0.73$ rounds with an interval that contains
it, and $0.15$--$0.35$ rounds on the other two, where it costs net
input tokens. On this executor success rates show no reliable change.
In the first run of Study~2 the treatment arm beat baseline by $+13$
of 102 (task, repetition) cells (McNemar $p=0.011$, Holm-corrected),
formally meeting the pre-registered promotion criterion. The
same-prompt control, however, rose $+9$ on an identical prompt. The
arms had run in sequence, and the baseline arm ran about 1.7 times
slower per round and timed out on 38 of 102 runs, against 23 and 21
for the other arms. We re-ran the study with the arms interleaved
under a new pre-registration. The artifact disappeared: per-round
speed differed by under 9\% between arms, the control did not differ
from baseline ($-6$ cells, $p=0.33$), and neither the memory against
baseline ($-7$, Holm $p=0.59$) nor its content against the control
($-1$, $p=1.00$) showed an effect. On the smaller executor of the replication the playbook
lengthens trajectories by up to $1.75$ rounds, costs $2.7$k--$6.6$k
net input tokens per task, and lowers the pre-registered pass rate on
one task of three ($10/20$ to $2/20$, Holm $p=0.041$).

This paper contributes:
\begin{enumerate}
\item the \emph{amortization condition} for prompt-injected
  procedural memory in agentic loops, an accounting identity used as a
  reporting convention: it splits the net token balance into the
  rounds an injected section saves and the overhead it adds, with
  per-task break-evens measured on two executors
  (Sections~\ref{sec:model} and~\ref{sec:results});
\item a pre-registered replication and a pre-registered, interleaved
  evaluation of project memory, reported with a reanalysis that
  separates functional correctness from token budgets and timeouts,
  and that lists every departure from the registered plans: the
  replication shows injected memory lengthening trajectories and
  lowering success on one task, and the interleaved run finds no
  effect of project memory;
\item a measured case of why a same-prompt control (an A/A arm) and
  interleaved arms matter in LLM-agent benchmarking: with arms in
  sequence, the control exposed an arm-level throughput artifact that
  a conventional A/B would have reported as a treatment effect, and
  interleaving the arms removed it (Section~\ref{sec:results-pm});
\item the multi-session benchmark design A$\to$B$\to$H for measuring
  procedural transfer under objective oracles, contributed as a design
  with a first partial instantiation rather than a completed
  benchmark: the pilot exercises sessions B and H against a
  human-written playbook, while the live tutor of session A remains
  future work (Section~\ref{sec:method});
\item a design lesson with measured directions rather than
  speculation: injected memory pays only if the injection cost drops
  (retrieval on demand) or the round savings rise (class-unlocking
  interventions) (Section~\ref{sec:discussion}).
\end{enumerate}

\section{Background and Related Work}\label{sec:related}
% /verify-refs pasa en S4 sobre las entradas nuevas (ver refs.bib).

\paragraph{Memory-augmented LLM agents.} Cross-episode memory is an
established lever in the agent literature. Voyager accumulates an
ever-growing library of executable skills that later episodes retrieve
and compose \citep{wang2023voyager}; Reflexion stores verbal
self-reflections from failed trials and conditions subsequent attempts
on them \citep{shinn2023reflexion}; MemGPT manages the context window
as virtual memory, paging information between the prompt and external
storage \citep{packer2023memgpt}. Later systems make the distillation
step automatic: Agent Workflow Memory induces reusable workflows from
an agent's own trajectories and injects them into subsequent tasks
\citep{wang2024awm}; ExpeL extracts transferable insights from
pools of past experience \citep{zhao2024expel}; Memp distills
trajectories into step-level instructions and script-like
abstractions, and reports that memory built with a stronger model
still helps a weaker one \citep{fang2026memp}; and ACE treats the
context itself as an evolving playbook, grown through generation,
reflection, and curation \citep{zhang2026ace}. A second branch keeps
memory outside the prompt and retrieves it on demand, from the memory
stream of Generative Agents \citep{park2023generativeagents} to
production memory layers that argue for retrieval precisely on cost
grounds \citep{chhikara2025mem0}; \citet{zhang2025memorysurvey}
survey the design space. These systems established that
memory \emph{can} improve agents, in evaluations centered on
frontier-scale models and success metrics. Cost-aware evaluation of
agents has been argued for in general \citep{kapoor2024agents}, but
what carrying a memory costs (on every round, in a loop that re-sends
its context) is rarely priced in memory evaluations, and the effect of the memory's \emph{content} is
rarely separated from the effect of perturbing the prompt at all. Both
gaps are the subject of this paper.

\paragraph{Repository context files.} In practice, the most widespread
form of prompt-injected memory is the repository context file
(\texttt{CLAUDE.md}, \texttt{AGENTS.md}) that a coding agent loads into
every session. Mining studies describe these files as
configuration-like artifacts that grow through frequent small
additions and that favor test procedures, implementation details,
and architecture
\citep{chatlatanagulchai2025manifests,chatlatanagulchai2026agentreadmes}.
A controlled evaluation on SWE-bench Lite and on repositories with
developer-written files found that context files did not significantly
change resolution rates, while generated files raised the average
number of agent steps by 2.45 and 3.92 on the two benchmarks and
inference cost by 20\% and 23\% \citep{gloaguen2026agentsmd}. That
study priced the overhead in API dollars, for three hosted models and
one locally served 30B coder whose cost it estimated from API prices.
Our cost findings partly replicate theirs at a smaller scale. The
ProjectMemory hook of Study~2 (Section~\ref{sec:method}) is a context
file of this kind, and the amortization condition states when the
added rounds and tokens would be repaid.

\paragraph{Concurrent work: evolved skills at larger scale.} While
this paper was under preparation, \citet{tang2026wikiskill} introduced
WikiSkill, which co-evolves agent skills with a persistent wiki and
reports large accuracy gains over no-skill baselines across five
benchmarks and five models. Read against our result the two are
complementary rather than contradictory, for three reasons. First, the
endpoints differ: WikiSkill measures accuracy and does not price the
context its skills occupy, even though those skills are injected in
full into the system prompt on every round and average between 45 and
143 markdown lines depending on model and benchmark --- precisely the
per-round tax whose break-even Section~\ref{sec:model} quantifies.
Second, the mechanism differs: their skills are evolved across
iterations under a validation gate with rollback, whereas ours is a
fixed human-written playbook, adopted as a strong a-priori condition
for content quality rather than as a competing optimizer. Third, their gains grow with executor capability ($+12.3$, $+17.5$ and
$+23.9$ points at 4B, 9B and 27B dense models). Our executors are not
directly comparable on that axis: one is a 20B mixture-of-experts with
$\sim$3.6B active parameters, the other a dense 9B, on which WikiSkill
reports $+17.5$ points while our injected playbook lengthens
trajectories without changing correctness. The divergence is consistent
with the different endpoints (accuracy there, rounds and tokens here)
and with the different memory (evolved skills there, one fixed playbook
here); we do not resolve it. Their design assumes the injection side is
affordable; this paper measures its price.

\paragraph{Small and local models as executors.} Surveys of small
language models document the capability and deployment trade-offs of
the sub-10B regime \citep{lu2024smalllm,corradini2025}; our executor,
a 20B mixture-of-experts with $\sim$3.6B active parameters, runs on
commodity hardware at the practical edge of that regime. Two
properties of this regime sharpen the memory question. First, under local
inference the input-token bill is paid in wall-clock time on the
user's hardware on every round, so per-round context overhead is a
first-order design cost, not a billing detail. Second, small executors
are sensitive to context additions in ways that are hard to predict:
the companion study to this paper measured harness levers one at a
time at small-model scales and found ``obviously good'' context
additions frequently null or harmful \citep{parra2026scaffolding}; that result
is the prior behind the honest expectations pre-registered here.
Compressing injected context is a complementary lever: models can
consume text that is no longer human-readable \citep{zhu2026babeltele}.
That lowers the per-round tax but leaves the amortization question
intact.

\paragraph{The harness as an engineering object.} SWE-agent showed
that the agent-computer interface changes outcomes at fixed model
\citep{yang2024sweagent}; practitioner curricula and post-mortems now
treat ``harness engineering'' as a named discipline
\citep{walkinglabs2026,dex2026wsff}, and LoopsBench extends the framing
from the harness to the whole evaluation loop \citep{li2026loopsbench}.
Practitioner-facing empirical work has begun to measure this layer
directly: interview studies find that configuring and steering agentic
frameworks is itself a recurring pain point for the developers who
operate them \citep{hamid2026hands}, and cost--benefit studies of
assistant output ask how many candidate solutions are worth inspecting
before returns diminish \citep{oertel2025copilot}; this paper takes
the same measurement-first stance toward injected memory.
Two recent results make the memory component specifically urgent.
CompInt quantifies silent \emph{loss}: user-issued side constraints
survive context compaction only a minority of the time, and the
authors close the gap with an extraction module separate from the
compactor rather than with better compaction prompts
\citep{wang2026compint}. AutoDesign formalizes the harness as a
recursive optimization target (a meta-harness optimizer proposes one
bounded update per iteration to one of five components, of which
Context \& Memory is one), accepting updates when a train score
improves and a dev score does not regress \citep{luo2026autodesign}.
Neither line prices the \emph{injection} side of memory.
Section~\ref{sec:discussion} argues that the amortization condition of
Section~\ref{sec:model} is the acceptance criterion that side needs,
and that in the small-model noise regime a point-estimate acceptance
gate would have promoted the false positive our control arm caught.

\paragraph{Negative results and pre-registration in empirical software
engineering.} Pre-registration separates hypothesis generation from
confirmation \citep{nosek2018preregistration}, and open-science
initiatives in empirical software engineering journals have
institutionalized the transparency and reproducibility expectations
that make a well-documented null
publishable \citep{mendez2019openscience}; community standards make
analogous demands on benchmark-based studies \citep{ralph2021standards},
and the statistical treatment of randomized SE experiments is
well-codified \citep{arcuri2011practical}. This paper follows that
discipline in a lightweight form: both runs of Study~2 and the
replication were registered by committing hypotheses, decision
criteria, and an honest prior to the project repository before launch,
while Study~1 is
reported as exploratory (Section~\ref{sec:method-prereg}); Study~2's
contrasts are paired exact tests with multiplicity correction, and
every endpoint family of Study~1 and the replication carries
Holm-corrected tests, a correction added for Study~1 in a reanalysis
after its data were collected.

\section{The Amortization Condition}\label{sec:model}
% Fuente: outline § "El claim que los datos SÍ sostienen". Sección
% CENTRAL y corta — la fórmula que Results instancia.

Prompt-injected procedural memory (a playbook, a list of files
touched in previous sessions, a distilled tutor intervention) enters
the agent's context on \emph{every} round of a turn: agentic
loops re-send the (growing) conversation to the model each round, so a
memory section of $c$ tokens does not cost $c$ tokens per task but
$c \times R$ tokens, where $R$ is the number of rounds the turn takes.
Its benefit, in turn, is realized as \emph{rounds saved}: if the
memory actually guides the model, the turn converges earlier.

Two clarifications about what that cost is, and is not. Modern
serving stacks cache the key--value state of a stable prefix, so an
injected section is \emph{computed} once rather than $R$ times; the
$c \times R$ term is therefore an accounting and occupancy cost, not
a recomputation cost. It is nonetheless real on three counts: hosted
APIs meter input tokens per round (discounted under explicit prompt
caching, not free); the cached section occupies key--value memory for
the whole turn, competing with the rest of the context, which is
material on constrained hardware; and carrying the section changes
what the model sees on every round, so its effect on the trajectory
is behavioral, not merely fiscal. Our own measurements separate these
components: on \textsc{loop} and \textsc{move} in Section~\ref{sec:results-m1}
the playbook adds ${\sim}1{,}100$ net input tokens with \emph{no}
reliable change in wall time (Table~\ref{tab:m1}), which is
consistent with a cached prefix, although latency dominated by
decoding would produce the same pattern and we did not record prefill
and decode times separately --- while on the weaker executor of
Section~\ref{sec:results-ornith} the same section lengthens
trajectories, which is the behavioral component and the one that
costs most. Equation~\eqref{eq:amortization} prices the
accounting term; the behavioral term enters it through $\Delta R$
(Section~\ref{sec:disc-anticorr}). For a practitioner whose
serving stack hides the accounting term from the wall clock behind a
cached prefix, the behavioral component is the operative risk;
Equation~\eqref{eq:amortization} remains the design-time acceptance
criterion for whether an injection should exist at all.

Let $R_{\mathrm{base}}$ be the mean rounds of the memory-free agent on
a task and $T_{\mathrm{base}}$ its input tokens per round, computed as
total input tokens over total rounds across the arm's runs; and
let $\Delta R = R_{\mathrm{base}} - R_{\mathrm{mem}}$ be the round
reduction the memory produces. Injection adds a per-round overhead
$\Delta T = T_{\mathrm{mem}} - T_{\mathrm{base}}$. The memory
\emph{amortizes} (saves net input tokens) if and only if

\begin{equation}\label{eq:amortization}
\underbrace{\Delta R \cdot T_{\mathrm{base}}}_{\text{rounds no longer
paid}} \;>\; \underbrace{\Delta T \cdot
R_{\mathrm{mem}}}_{\text{overhead on every surviving round}} .
\end{equation}

Equation~\eqref{eq:amortization} makes the trade explicit: a memory
section that costs a few hundred tokens per round must buy a
substantial fraction of a round to break even. With $T$ defined as a
ratio of totals, it is an accounting identity: the difference between
its two sides equals the measured net change in input tokens per task,
exactly. It is therefore not a predictive model and not a finding in
itself. It is a reporting convention: it splits the net token balance
into the rounds the memory saves and the overhead it adds, so that a
reader can see which term moved. Two quantities in it need care.
$\Delta T$ is the measured difference in input tokens per round, which
includes the injected section and any change in what the trajectory
carries; it is not the size of the injected section alone. And the
break-even $\Delta R^{*} = \Delta T \cdot R_{\mathrm{mem}} /
T_{\mathrm{base}}$ is task-specific. Written as $\Delta R^{*} =
(\Delta T / T_{\mathrm{base}}) \cdot R_{\mathrm{mem}}$, it scales with
the relative overhead and with the length of the trajectory. For the
three tasks of Study~1 ($T_{\mathrm{base}} \approx 1{,}400$ tokens per
round, $\Delta T \approx 180$--$270$), $\Delta R^{*}$ is $0.73$,
$0.92$ and $1.16$ rounds; on the 9B executor of the replication it is
$1.02$, $1.74$ and $1.68$. In this regime of short trajectories and
small contexts, the memory must eliminate about one full round of
interaction to pay for itself. The bar is a property of the regime,
not of injected memory: in a long-context session with
$T_{\mathrm{base}} = 20{,}000$ tokens per round and $R_{\mathrm{mem}}
= 20$, the same 300-token overhead breaks even at $0.3$ rounds. The
empirical question for this paper is whether a human-written playbook
clears the bar in the measured regime. Its point estimate clears it on
one task of three on the 20B executor, with an interval that also
contains the break-even, and on none on the 9B executor
(Section~\ref{sec:results}).

\section{Method}\label{sec:method}

\subsection{Harness, model, and benchmark
infrastructure}\label{sec:method-harness}

Both studies run on \braze{}, a local-first agentic coding harness
written in Rust whose design and evaluation methodology are described
in a companion study \citep{parra2026scaffolding}. The harness executes the
standard agentic loop: a system prompt carrying the tool inventory
(and, when enabled, a memory section), followed by \emph{rounds} in
which the model emits tool calls, the harness executes them in a
sandbox, and the tool results are appended to the conversation. The
property that drives Equation~\eqref{eq:amortization} is structural,
not incidental: on every round the harness re-sends the entire growing
conversation, including any injected memory section, so a
$c$-token memory costs $c \times R$ input tokens per task, not $c$.

The executor model in both studies is \texttt{gpt-oss:20b}, a
mixture-of-experts model (20B total, $\sim$3.6B active parameters)
running on a dedicated LAN inference node (16\,GB RAM); no other
workload shares the node during a sweep. The first run of Study~2 was
interrupted by a $\sim$16.7\,h suspension of the node, during which
the monotonic clock that per-task timeouts use does not advance. Study~1 serves the model
through an Ollama server; both runs of Study~2 use \braze{}'s in-process
\texttt{LocalBackend} (llama.cpp through the \texttt{llama-cpp-2}
0.1.152 bindings, with the model's canonical Harmony chat template and
the reference \texttt{gpt-oss-20b-MXFP4} GGUF weights, SHA-256
\texttt{27cd6c43\ldots ae35901}), with context window 32{,}768 tokens,
output cap 12{,}288 tokens, temperature 0.2, and a 900\,s per-task
timeout. The hash was computed after the first run, on a file whose
modification date (2026-07-21) precedes it. The run metadata records
the sampling settings, seed, timeout, suite fingerprint, harness
commit, model digest (Study~1 and the replication), and server version
(replication only). For the first run of Study~2 it records only two
backend variables: the context window and output cap were set through
environment variables it did not capture, and neither the GPU
placement nor per-run start times were recorded. The interleaved run
records all four environment variables, the llama.cpp binding version,
the run order and its seed, and the start and end time of every run;
its log records the GPU placement (25 layers on the GPU, key--value
cache in host memory), loaded once and shared by the three arms. Each benchmark run receives a hermetic sandbox (a
fresh directory containing only the task's setup files) and is graded
by scripted assertions: expected content in the resulting files
(substring checks), per-task budgets of rounds and, in Study~1 and its
replication, of input tokens (8 rounds and 12{,}000 input tokens per
task), and a real \texttt{cargo check} on the resulting tree. The
\texttt{cargo check} assertion entered the benchmark on 2026-07-18,
after Study~1 had run: Study~1's pass/fail is therefore based on file
content and budgets only, while the replication and Study~2 include
\texttt{cargo check}. Because an input-token budget penalizes any
per-round injection mechanically, we report \emph{functional
correctness} (expected file content, \texttt{cargo check} where
available, no timeout) separately from budget compliance
(Section~\ref{sec:results}). The runner records
pass/fail, rounds, input and output tokens, wall time, and schema
validation failures per run.

\subsection{The two memory mechanisms under
test}\label{sec:method-mechanisms}

\paragraph{LearnedPlaybook (Study 1).}\sloppy A typed unit of
procedural memory defined by a JSON Schema: identity and lifecycle
fields, a procedural payload (\texttt{task\_family}, \texttt{applies\_when},
\texttt{preconditions}, \texttt{method\_steps}, \texttt{verification},
\texttt{avoid}, \texttt{escalate\_if}), and provenance
(\texttt{source}, \texttt{evidence}). The lifecycle is
\texttt{candidate} $\to$ \texttt{approved} $\to$ \texttt{validated}
$\to$ \texttt{trusted} (or \texttt{retired}); in the distillation
design, approval of a candidate requires only safety checks (schema
validity, no sensitive data, no concrete file names from the source
session, objective verification steps, an escalation clause); no
semantic hand-editing is allowed, so that tutor distillation is not conflated
with human authorship. The benchmark injects a playbook by rendering
it as a structured text section (title, family, applies-when, method,
verification, avoid, escalate-if) into the system prompt, truncated by
whole lines under a fixed 500-token budget. In Study~1 the playbook is
\emph{human-written} (a strong condition a priori for content
quality: no distillation noise). It does not bound shorter or more
targeted variants, whose injection cost could be lower
(Section~\ref{sec:results-cost}). Its rendered text, 1{,}194
characters ($\approx$299 tokens by the benchmark's
four-characters-per-token estimate), is reproduced verbatim in
Appendix~\ref{app:artifacts}.

\paragraph{ProjectMemory hook (Study 2).} The production form:
a harness hook that listens on the engine's event bus and records,
deterministically and with zero model calls, the paths of files
successfully written or edited into a small per-project JSON state; at
the start of a new session the harness renders a capped ``project
memory'' section (files touched in previous sessions) into the system
prompt. The capture is deliberately deterministic, with no model-written
summaries, because the same project had previously measured that
free-prose context degrades small executors. The lever is off by
default and enabled per-arm by the benchmark's ablation flags.

\subsection{Study 1: the multi-session benchmark
A$\to$B$\to$H and pilot M1}\label{sec:method-m1}

The benchmark models procedural transfer across sessions. In session
\textbf{A} the local model fails a task under an objective check and a
tutor intervention produces a playbook; \textbf{B} tasks are
same-family tasks with different modules, names, and constants, and
measure whether the playbook transfers; the holdout \textbf{H} is a
task outside the family and measures what an inapplicable playbook
costs. The pilot reported here (milestone M1) runs the benchmark
without a live tutor: the playbook is the human-written ceiling
described above, for the family \texttt{rust\_compile\_repair}
(borrow-checker repair in Rust).

The three B tasks were chosen to span the family: \textsc{original}
(the canonical E0502 borrow bug), \textsc{loop} (E0502 arising through
iteration), and \textsc{move} (E0382, use of moved value). The holdout
is a Rust task not involving borrow errors, run \emph{with} the
playbook attached. Arms are \texttt{none} vs.\
\texttt{human-playbook}, $n=20$ per cell with identical seeds
(42--61) and backend across arms: $7$ task-arms $\times\, 20 = 140$
runs. Following the pilot's own first finding, we report the three
quantities of Equation~\eqref{eq:amortization} together (round
reduction $\Delta R$, per-round overhead $\Delta T$, and net token
delta) so a reader can distinguish ``the playbook saved rounds''
from ``the playbook cost nothing'' from ``the playbook cost but the
turn was short anyway.'' Pass rates are compared with Fisher's exact
test and pass-rate differences carry Newcombe 95\% intervals; rounds
and wall time use two-sided Welch $t$-tests with Welch intervals,
Holm-corrected across the three task pairs within each endpoint
family. Table~\ref{tab:m1} reports point estimates; inference is in
the text. The pilot was sized for the efficiency endpoints, not pass
rate: at $n=20$ per cell, Fisher's exact test resolves only very large
pass-rate differences: by simulation from a base rate of $0.7$, power
is $0.84$ for a drop of $0.5$, $0.59$ for $0.4$ and $0.34$ for $0.3$.
Moderate success-rate effects are therefore out of reach by
construction. The minimum detectable change in rounds at $80\%$ power
is $0.45$--$0.95$ rounds per task on gpt-oss:20b and $0.84$--$2.09$
on ornith:9b, of the same order as the break-evens, so the round
endpoints can resolve an effect the size of a break-even but not a
fraction of it.

The 140-run sweep reported here is the only full-size run of the final
three-task suite (suite fingerprint \texttt{a5fccc8f}). The repository
also holds 17 development files for this study (smoke runs, mechanism
diagnostics, and a 100-run sweep of an earlier suite version whose
outcomes differ, e.g.\ \textsc{loop} $17/20\to15/20$); all are listed
with their fingerprints in the reanalysis report. The suite file at the
commit recorded in the run metadata does not yet contain the
\textsc{loop} and \textsc{move} tasks: the exact suite text at run time
was not committed, which we disclose rather than reconstruct.

Study~1 was subsequently replicated on a second executor:
\texttt{ornith:9b} (Ornith AI; a dense 9B-parameter model of the
Qwen3.5 architecture family, Q4\_K\_M quantization, Ollama registry
digest \texttt{a75697c14589}) that
saturates the project's easier benchmark suite, served through the
same node with a 300\,s per-task timeout. The two executors are chosen
to span the axis that matters for this regime rather than to sample it
exhaustively: a sparse mixture-of-experts (gpt-oss:20b, $\sim$3.6B
active) and a dense model (ornith:9b) of different provenance, both at
the practical edge of commodity local inference and both strong enough
to saturate the project's easier suite unaided --- so a memory effect
here cannot be dismissed as merely rescuing a model that was failing
anyway. The replication was
pre-registered before launch with the same design, seeds, arms, and
analysis plan, plus one rule specific to replication: any classification of the
tasks by difficulty is re-derived from the memory-free arms alone,
before any playbook arm is read. The earlier version of this paper
labelled \textsc{original} as the task the model already knew; the
memory-free arms of Study~1 contradict that label
(Section~\ref{sec:results-m1}), and this version does not use it.

\subsection{Study 2: project-memory A/B with a same-prompt
control}\label{sec:method-pm}

Study 2 evaluates the ProjectMemory hook on \braze{}'s discriminating
suite: 34 editing tasks with a \texttt{cargo check} oracle, calibrated
near the executor's capability frontier ($\approx$2.9\,pp per item).
Three arms: \texttt{baseline} (hook off), \texttt{empty} (hook on;
since the benchmark opens a fresh session per repetition, the memory
is always empty and renders nothing: the same-prompt control), and
\texttt{seeded} (hook on; the benchmark synthesizes the memory a
previous session would have left, using the task's own setup files as
the touched-file list, with zero experimenter-authored content). Three
repetitions per arm at fixed seed and temperature 0.2 give $3 \times 3
\times 34 = 306$ runs. The primary contrast is pass rate under
McNemar's exact test on (task, repetition) pairs, Holm-corrected
across the two contrasts against baseline. Because repetitions of the
same task share prompt and oracle, pair-level McNemar overstates the
effective sample; we therefore also report task-level (cluster-aware)
tests: an exact sign test and an exact Wilcoxon signed-rank test
(zeros dropped, exact null by enumeration of signs) over the 34
per-task pass counts. They were added post hoc to the first run and
registered for the second. Secondary metrics are input tokens, rounds,
and wall time.

\paragraph{First run: arms in sequence (August 2026).} The three arms
ran one after another (baseline, then empty, then seeded), each as a
separate invocation of the benchmark that loaded the model on its own.
The decision criteria were pre-registered before launch:
(1)~a \emph{plumbing gate}, evaluated first: if the empty arm
differs from baseline by more than 2 paired discordant cells, the
infrastructure is investigated before any other contrast is read;
(2)~a promotion signal (\texttt{seeded} $-$ \texttt{baseline} $\geq
+3$ tasks with $p<0.05$ \emph{and} \texttt{seeded} $\geq$
\texttt{empty}), which at most \emph{opens} a promotion discussion,
since the study measures only the single-session prompt-side effect,
not cross-session value; (3)~a symmetric harm criterion; (4)~the null
as the declared expectation (the registered prior: null or slightly
negative, since the touched-file list adds little the task prompt does
not already say, and costs tokens per round); and (5)~no iteration
allowed: the sweep is a measurement, not a tuning loop.

\paragraph{Second run: arms interleaved (November 2026).} The first
run's arms differed in throughput, so arm and run order were
confounded (Section~\ref{sec:results-pm}). We re-ran the same design
under a new pre-registration with three changes. The arms run in one
invocation that loads the model once for all three. Within each
(repetition, task) block the three arms run in a random order, drawn
with a recorded seed, so that any drift of the node spreads across
arms instead of separating them; blocks run repetition by repetition.
And the run records its environment, order, and per-run times. The
registered hypotheses are, in order: H1, the empty arm does not differ
from baseline (a validity check, read first: if it fails, the run
cannot measure the lever); H2, seeded differs from baseline; H3,
seeded differs from empty. The first run's plumbing gate of at most 2
discordant cells is replaced by McNemar $p\geq0.05$ for H1: the first
run had shown that many more than 2 cells can change between runs of
an identical prompt, so the old threshold could not be met by design
(the registration declares this as a deviation); the promotion and harm
criteria are unchanged. The registration also fixes the validity rules
(infrastructure failures above 10\% invalidate the run; a difference of
more than 20\% in seconds per round between arms, or a gap of more than
10 minutes between runs, is declared) and the analysis of timeouts as
censoring.

\subsection{Pre-registration and
reproducibility}\label{sec:method-prereg}

The project follows a git-only registration convention: each
hypothesis document --- research question, arms, metrics, decision
criteria, and an honest prior --- is committed to the project's public
repository before its sweep is launched. The order of registration
and data can then be checked against the public commit history. Git
timestamps are set by the author, so this establishes order within
that history, not precedence certified by a third party. Two features
of the record make later tampering detectable: every run of Study~2's
first sweep names its registration commit (\texttt{c84e1c3}) as the
harness commit it ran on, and the replication ran on a commit
(\texttt{2f07ce5}) that follows its registration (\texttt{b2fb8d9})
without any change to the harness code. For the interleaved run of
Study~2 there is also third-party evidence: GitHub records the push of
its registration (\texttt{15d74ca}) at 23:16:57 UTC on 2026-11-19,
before the first launch at 23:21:31 UTC, and the push of its amendment
(\texttt{0fe2725}) at 20:44:52 UTC on 2026-11-21, before the valid
launch, whose first run started at 21:00:21 UTC and ran on that commit.

We audited our own compliance, and it is asymmetric. The order is
externally verifiable for both runs of \textbf{Study~2} (first run:
hypothesis committed 2026-08-04, first data 2026-08-06; interleaved
run: registration 2026-11-17, pushed 2026-11-19) and for the
\textbf{replication of Study~1} (hypothesis 2026-08-15, data
2026-08-16). For each document
and data file, \texttt{git log --diff-filter=A --format='\%h \%ad'
-- <path>} prints the commit that added it; \texttt{--follow} should
not be used, because git's copy detection then reports a spurious
earlier addition for some data files. It is
\emph{not} verifiable for the Study~1 pilot itself, whose protocol,
hypothesis, decision record and data all entered the public
repository in one commit after the pilot had run. Those documents
carry earlier internal dates and were written before the sweep, but
external precedence cannot be established from the record, and we do
not ask the reader to take it on trust. We therefore report the
pilot as \emph{exploratory} and rest this paper's confirmatory claims
on the replication and the interleaved run of Study~2, whose
registration is verifiable. The first run of Study~2 was registered
too, but its own validity check failed (Section~\ref{sec:results-pm}),
so we report it as the case that motivated the second run.
Study~1's Holm correction was added in a reanalysis on 2026-08-15,
after its data had been collected. Table~\ref{tab:deviations} lists
every departure of the reported analyses from the registered plans.
The interleaved run has one amendment, committed and pushed before its
valid launch: the first launch of that run went out without the Rust
toolchain on the process's path, so neither the agent's nor the
oracle's \texttt{cargo check} could run, and it was declared invalid
for that instrument failure and repeated in full with the same plan
and seed. Before declaring it invalid we had looked at run counts,
failure causes, total passes and the per-arm seconds per round; no
per-arm pass-rate contrast was read. Its records are archived and
marked as invalid. The replication's hypothesis document also refers to a
simulated pre-submission review stored outside the repository; that
review motivated the replication and did not change its design.

The pre-registered hypothesis H1 predicted that $\Delta R$ would be
larger on the task the executor solves best unaided than on the
others, and that net tokens would be positive wherever $\Delta R <
\Delta R^{*}$. Classifying the tasks from the memory-free arms alone,
as registered, \textsc{original} is the one ornith:9b solves best
($16/20$). The observed order matches the prediction ($-0.50$ against
$-1.55$ and $-1.75$), net tokens are positive on all three, and the
registered verdict was ``replicates''. We do not lean on that
verdict: with three tasks a rank order is not a test, and on Study~1's
executor the same classification is contradicted by the memory-free
arms (Section~\ref{sec:results-m1}). Table~\ref{tab:deviations}
lists this and the other departures from the registered plans.

The replication therefore moves the measurement in one direction: on
the 9B executor the playbook is not merely unprofitable; it makes the
agent take longer, and on one task of three it lowers success. The a-priori plausible
expectation that a weaker model has more rounds of headroom for memory
to save is measured here and refuted: the weaker executor spends more
rounds with the playbook, not fewer, consistent with the companion
study's finding that injected prose context can harm small executors
\citep{parra2026scaffolding}.

\subsection{Study 2: an order artifact, and a null once the arms are
interleaved}\label{sec:results-pm}

The second study evaluates the harness-integrated form of the same
idea: a project-memory hook that injects, into the system prompt, the
files touched in previous sessions. Because the benchmark opens a
fresh session per repetition, the plain hook arm runs with empty
memory and renders \emph{nothing}: its prompt is identical to the
baseline by construction. That accident of plumbing makes the empty
arm a \textbf{same-prompt control}: any paired discordance between it
and the baseline measures, inside the same sweep, everything that is
not the treatment, noise and any drift between arms. A third arm
(\emph{seeded}) synthesizes the memory a previous session would have
left, with zero experimenter-authored content; this exercises the
production \emph{injection} path with synthetic capture --- running
the capture path across real sessions end-to-end is outside this
study's scope. That content is deliberately thin (a list of files the
task prompts largely repeat, as the pre-registered prior already
noted), so this study bounds the attributable effect of a realistic
cheap injection; probing rich procedural content is Study~1's role.

\paragraph{First run: the control exposes an order artifact.}
Table~\ref{tab:pm} reports the first run, with the arms in sequence.
Read without the control arm, it is a publishable positive: seeded
beats baseline by $+13$ cells ($12.7$\,pp), McNemar $p=0.011$, Holm
$p=0.021$, meeting the pre-registered promotion criterion \emph{in its
letter}. The control arm invalidates the premise: with a byte-identical
prompt, the empty arm rose $+9$ on its own, and the only contrast that
isolates the \emph{content} of the memory (seeded vs.\ empty) is null
($+4$, $p=0.541$). At task level, the headline contrast weakens to an
exact sign test $p=0.065$ and an exact Wilcoxon $p=0.051$
(normal-approximation variants give $0.033$ to $0.067$).

The pre-registered plumbing gate had fired first: baseline and empty
differed in 21 paired cells against a threshold of $\leq 2$. A
diagnostic on preserved sessions found round-1 prompts token-identical
across arms in all 12 pairs, and at the time we read the discordance
as noise. The reanalysis identifies a more specific source. The
baseline arm ran at a median of 100\,s per round against 58 and 61\,s
for the other two, and timed out at the 900\,s cap on 38 of 102 runs
against 23 and 21. The slowdown holds among runs that did not time out
($89.7$ against $53.8$ and $54.8$\,s per round), so it is not a
consequence of the timeouts. The run metadata cannot identify its
cause. A candidate, which we can neither confirm nor exclude, is GPU
placement: each arm ran as a separate invocation that fitted the
model's layers to the GPU memory free at load time, and this was not
recorded. Because the arms ran in sequence, arm and run order were
confounded, and this run cannot measure the effect of project memory
in either direction.

\subsection{Cost of the injected section}\label{sec:results-cost}

% síntesis M1 (200-270 tokens/ronda del playbook).
The two studies bracket the injection-cost regime that
Equation~\eqref{eq:amortization} prices. The M1 playbook raises input by
$\sim$180--270 tokens \emph{per round} on the 20B executor
(Table~\ref{tab:m1}); the project-memory section is small
($\sim$40 tokens in round 1) but correspondingly carries no measurable
content signal. Between them: the injection cheap enough to be
harmless was too thin to matter, and the injection rich enough to
matter was too expensive to amortize on two of three tasks. Two caveats
bound this reading. The two points differ in content type as well as
size, and they come from different studies and serving stacks; and
the middle of the
size axis is unmeasured: a short, task-tuned procedural hint of,
say, 50 tokens would face a break-even of only $\sim$0.2 rounds under
Equation~\eqref{eq:amortization}, and the variant that carries the
memory only for the first rounds of a turn and then drops it halves
the tax at fixed content. The frontier is narrow at its measured
points; the middle of the axis is open.

\subsection{A reminder, not a teacher, on this
evidence}\label{sec:disc-anticorr}

On the 20B executor the playbook did not change whether the model
reached a fix; at most it changed how long the model took. On the 9B
executor it lowered success on one task of three
(Section~\ref{sec:results-ornith}). The logged
tool-call sequences of Study~1 show the model following the advice on
\textsc{loop} and \textsc{move} without arriving faster for having
read it. Round savings, where they occur, come from skipping
deliberation the model can already do; they do not come from making
hard reasoning easier. In that sense prompt-injected procedural memory
behaved here as a reminder, not a teacher. With one playbook and three
tasks, this is a description of what we measured, not a law.

Across all $n=20$ runs per cell on \textsc{loop} and \textsc{move}
(80 trajectories), we extract two proxies directly
from the logged tool-call sequences, rather than hand-coding a subset:
whether a run reaches a code edit (\texttt{edit\_file}, effectively the
fix --- $56$ of the $62$ passing fresh runs issue exactly one), and how
many tool calls precede that first edit. Both say the same thing. First,
the playbook does not change \emph{whether} the model reaches a fix: the
fraction of runs that issue a code edit is flat (\textsc{loop}
$16/20\to19/20$, Fisher $p=0.34$; \textsc{move} $20/20\to20/20$), and
pass rate is flat-to-negative (Table~\ref{tab:m1}) --- the advice does
not unlock tasks the model would otherwise fail, which is what a teacher
would do. Second, where the playbook trims anything, it trims a fraction
of a step of front-loaded deliberation, not a restructured solution:
the tool calls preceding the first edit move by at most $\sim$0.35
(\textsc{loop} $2.75\to2.47$, Mann--Whitney $p=0.48$; \textsc{move}
$3.40\to3.05$, $p=0.023$, Holm $0.045$ across the two tasks) --- the same small magnitude as the round
reduction itself. Total tool calls tell the same story:
indistinguishable on \textsc{loop} ($4.60\to4.45$, $p=0.80$) and
shifted by $0.35$ on \textsc{move} ($5.40\to5.05$, $p=0.029$, Holm
$0.059$), matching
its round reduction, which does not survive Holm correction
(Section~\ref{sec:results-m1}). The model applies the same fix by the same route
with or without the advice; the reminder shaves deliberation it can
already do, never the $0.92$--$1.16$ rounds the injection cost demands
on these two tasks.

The holdout points the same way: an inapplicable playbook costs its
per-round price without derailing the model. On the 9B executor the
same playbook goes from unprofitable to costly: $\Delta R$ turns
negative on every task. The logged tool calls suggest why. The
playbook tells the model to run \texttt{cargo check} after each edit
and, if the module has one, the closest unit test
(Appendix~\ref{app:artifacts}). On
ornith:9b, shell commands per run rise from $0.80$, $0.55$ and $0.50$
to $1.70$, $1.70$ and $1.65$ (Mann--Whitney, Holm $p\leq0.009$ on all
three tasks), roughly one extra command per run, the size of the
added rounds. On gpt-oss:20b they do not move ($1.90\to1.95$,
$1.50\to1.75$, $1.85\to2.00$, Holm $p\geq0.49$); what falls there is
file reading on \textsc{original} ($2.05\to1.20$, Holm $p<0.001$).
The most economical reading is that the smaller model follows the
playbook's verification steps literally and pays a round for each.
The run records keep tool names, not arguments, so we cannot confirm
that the extra commands are \texttt{cargo check}. If the reading
holds, the cost on this executor comes from what the playbook
prescribes, not from extra context as such, and the oracle, which
checks file content, gives no credit for the verification the extra
rounds buy. Separating the two would take an ablation of the
playbook by section, which we did not run.

\subsection{Why the null is worth publishing}\label{sec:disc-null}

``Distill the cloud tutor's intervention into a reusable playbook and
amortize the escalation'' is exactly the kind of technique that sounds
obviously good: plausible mechanism, appealing economics, easy to
adopt without measurement. Our original protocol for this line
proposed it as a positive contribution; the data refused. The project
this work belongs to has accumulated a discipline of pre-registered
null results at the harness level: a prose planner that actively
harmed small executors, tool deferral that proved cheaper but not
free, constrained decoding that failed to beat the harness's own
repair ladder \citep{parra2026scaffolding}. The present null is the highest
conceptual stake among them because the technique is the most
attractive. Neither the efficiency endpoints (Study~1 and its
replication) nor the interleaved run of Study~2 showed a benefit. A
null is bounded by what the design can detect, and here that bound is
coarse: about half a round to one round per task on gpt-oss:20b, a
drop of about $0.4$--$0.5$ in success proportion at $n=20$ per cell
(Section~\ref{sec:method-m1}), and 13 cells ($12.7$\,pp) for the
contrasts of Study~2's interleaved run. Benefits smaller than these are not
excluded. What
survives is quantitative and reusable: the per-task bar a memory must
clear ($0.73$--$1.74$ rounds across the tasks and executors measured
here) and a measured shortfall on two of three tasks.

\subsection{The same-prompt control and interleaved arms, measured}\label{sec:disc-control}

Without the empty arm, the first run of Study~2 is a publishable false
positive: $+13$ cells, McNemar $p=0.011$, Holm-corrected, meeting a
pre-registered promotion criterion. The control arm, whose prompt is
identical to baseline by construction, rose $+9$ on its own. Our
original reading attributed that rise to cell-level noise near the
capability frontier. The reanalysis of Section~\ref{sec:results-pm}
showed something more specific: the arms differed in throughput, and
the baseline timed out far more often. The interleaved run settles
what the first run could only suggest. With the arms in one invocation
and in random order, per-round speed differed by under 9\%, the
control did not differ from baseline, and the $+13$ became $-7$.
An earlier version of this paper also reported a re-run on a saturated
suite (0 of 190 within-task pairs flipping) as evidence that the noise
was a property of the suite rather than of the serving stack. That
measurement cannot support the claim: a suite on which every run
passes cannot produce a flip, and its trajectories did diverge (56 of
the 190 pairs ended with different outcome fingerprints). We withdraw
that attribution.

What survives is a demonstration, not a new instrument. A same-prompt
arm is what online experimentation calls an A/A test, a standard check
that the experimentation infrastructure itself produces no difference
\citep{kohavi2020trustworthy}, and running arms in an interleaved or
randomised order to protect against drift is a basic principle of
experimental design. The first run of Study~2 followed the first
principle and not the second; the interleaved run followed both. What
this study adds is a measured case of what each principle prevents in
LLM-agent benchmarking: the A/A arm flagged the artifact, and
interleaving removed it. Non-determinism in LLM code
generation is a documented threat to conclusion validity: for
ChatGPT, identical prompts yield programs with different test
outcomes, and a temperature of zero reduces the effect without
removing it \citep{ouyang2025nondeterminism}. A same-prompt arm cannot tell noise
from arm-level drift, but it detects both: any difference between it
and the baseline is a difference no treatment caused. Measured inside
the interleaved sweep, that floor is 26 of 102 cells (25\%) differing
between two identical prompts. In a regime where suites sit near the
capability frontier and a whole arm can run slower than another on the
same node, the only floor that can be trusted is one measured inside
the same sweep, and the arms should be interleaved rather than run in
sequence, so that drift spreads across arms instead of separating
them. The control is cheap (one extra
arm), demands no new tooling, and converts ``significant against
baseline'' into the question that matters: significant against
\emph{what}.

\subsection{Two measured exits from the wrong side of the
frontier}\label{sec:disc-directions}

Equation~\eqref{eq:amortization} has exactly two exits, and the data
locate both. \emph{Lower $\Delta T$}: move the memory out of the
per-round prompt and retrieve it on demand (a tool call or a
just-in-time context file), so its cost is paid once per consultation
rather than $R$ times per task. The condition then compares one
retrieval against rounds saved, a far weaker bar than the
$\sim$1{,}200 tokens per task the M1 playbook pays before helping.
Prompt compression lowers $\Delta T$ without moving the memory out of
the prompt \citep{jiang2023llmlingua,zhu2026babeltele}.
Retrieval-based memory systems already live on this side of the
condition \citep{park2023generativeagents,chhikara2025mem0}, though
their evaluations report quality, not the injection trade
Equation~\eqref{eq:amortization} prices.
\emph{Raise $\Delta R$}: target interventions at task classes the
model fails outright, where success converts a full budget of burned
rounds into a short trajectory and $\Delta R$ is large by
construction. The replication tempers this exit: on the 9B executor
injected guidance lengthened trajectories without improving
correctness, so a class-unlocking intervention must clear a behavioral
bar, not only an economic one.
The M1 playbook did the opposite: it encoded a
methodology for a family the model already navigates, which is why
its best case was worth only one round. To be precise about what is
measured: this paper quantifies the bar these designs must clear (the cost
structure of Equation~\eqref{eq:amortization} with the numbers
above), not the designs themselves, which remain future work with a
priced target. A third boundary is
scoped out deliberately: session-scoped constraints (user rules that
must survive context compaction) are the limit case of durable memory
whose value is \emph{compliance} rather than round savings.
Equation~\eqref{eq:amortization} does not price them, and a separate
pre-registered experiment in the same project addresses them. It has
since closed without adopting the lever: a pilot on the 9B executor
favoured the route ($5/40$ against $0/40$, $p=0.0625$), but the
pre-registered replication reversed it ($5/80$ against $8/80$ for the
control, McNemar $p=0.55$, with $18\%$ more input tokens), and the
lever was rejected. Neither outcome is something our condition can
price.

\subsection{Relation to compaction loss and meta-harness
optimization}\label{sec:disc-related}

Two recent lines make the context-budget economics of agent memory
urgent. Work on compaction loss \citep{wang2026compint} shows that the
harness silently \emph{loses} memory: session-scoped constraints
survive context compaction only a minority of the time, and the
authors argue for architectural separation of durable state. Our
result is the complementary half of the same budget: even when memory
is durably preserved and injected, the injection itself carries a
per-round price that two of three tasks do not repay. A principled memory
subsystem has to price both sides (what to preserve across
compaction and what to re-inject per round), and
Equation~\eqref{eq:amortization} is the acceptance criterion for the
injection side.

Meta-harness optimization \citep{luo2026autodesign} formalizes the
harness as an optimization target with memory as one of its
components, accepting a proposed harness update when a train score
improves and a dev score does not regress: point estimates, no
statistics. Study~2 is a concrete demonstration of what that
acceptance gate would do in this regime: it would have accepted a
$+13$-cell improvement that a same-prompt control flagged and an
interleaved re-run turned into $-7$. In the small-model regime, where
suites sit near the capability frontier and a whole arm can drift
relative to another, an automated harness optimizer needs the
machinery used here (pre-registered criteria, paired exact tests
with correction, a same-prompt control arm, and interleaved arms) as
its acceptance gate, or its optimization record fills with noise
promoted to design.

\section{Threats to Validity}\label{sec:threats}
% Fuente: outline § threats.

\paragraph{External validity.} Study 1 uses one task family
(\texttt{rust\_compile\_repair}); its result is measured on two
executors of different architecture (a 20B mixture-of-experts and a
dense 9B) on one hardware and serving tier, while Study 2 uses the
20B alone. The frontier remains configuration-dependent: a different
task family might admit interventions that unlock whole classes of
failure rather than shave steps off a known procedure, which would
move the break-even point. The once-plausible expectation that a
weaker model has more rounds of headroom for memory to save is no
longer a speculation we owe the reader: the replication measured it
and found the opposite (Section~\ref{sec:results-ornith}). The scale
of the break-even is also a property of the regime: the tasks run three
to seven rounds at about $1{,}400$--$1{,}900$ input tokens per round,
and with longer trajectories or larger contexts the same overhead
breaks even at a fraction of a round (Section~\ref{sec:model}). The
memory we test is one human-written checklist, not a memory distilled
from an observed failure, so the results do not speak for memories
that carry task-specific information. We claim the \emph{condition},
as a reporting convention, and the measurement procedure as general,
and the measured \emph{positions} of the frontier as specific to
short compile-repair tasks in this family and these two executors.

\paragraph{Construct validity.} The null concerns memory \emph{in the
prompt}. Retrieval-on-demand memory has a different cost profile by
construction and is untested here; we present it as the measured
design direction (Section~\ref{sec:disc-directions}), not as a
finding. The original protocol's remaining conditions
(\texttt{summary}, distilled \texttt{procedural},
\texttt{lead-fallback}) were not piloted. Each carries an injection
cost of its own, and a shorter or more targeted variant could cost
less than the human-written playbook, so their outcome is not implied
by ours and remains untested. The oracle is a second construct
threat: Study~1's pass/fail rests on substring checks and budgets
without \texttt{cargo check}, and an input-token budget mechanically
penalizes any injection; we therefore report functional correctness
separately and rest no conclusion on Study~1 pass rates. Finally,
``pays'' is defined narrowly: Equation~\eqref{eq:amortization} counts
the executor's input tokens. It does not price the escalation to a
cloud model that motivates the technique (session A was not run),
output tokens, or the value of a success. A memory that raised
success while costing net tokens would fail our condition and could
still be worth adopting.

\paragraph{Internal validity and reliability.} The serving stack is
not bit-exact under fixed seeds: in Study 1, a wall-time effect that
was significant in one sweep ($p=0.008$) did not replicate in an
independent re-run, while the primary token effect replicated in
direction and magnitude; no conclusion in this paper rests on a
secondary wall-time contrast. In the first run of Study~2, the
pre-registered plumbing gate fired (21 discordant cells against a
threshold of $\leq 2$), and the reanalysis traces the difference to an
arm-level throughput difference with more timeouts in the baseline arm
(Section~\ref{sec:results-pm}); because the arms ran in sequence, run
order and arm were confounded, and the cause was not identified. We
did not repair that run post hoc. We repeated it with interleaved arms
under a new registration, and only the repeated run carries
confirmatory weight. Its harness commit is later than the first run's
(\texttt{0fe2725} against \texttt{c84e1c3}); the suite is the same, but
absolute pass rates differ between the runs (baseline $59$ against
$77$ of 102), so the two runs are compared through their within-run
contrasts only. Its first launch was invalid and was repeated under a
documented amendment (Section~\ref{sec:method-prereg}). The
replication is conceptual rather than exact: the executor, the oracle
and the server version changed together, so differences between the
two executors cannot be attributed to the executor alone. All
headline contrasts use exact tests and are corrected for multiplicity
within each endpoint family; the decisive contrast is read against an
in-sweep same-prompt control rather than an imported floor; and both
pre-registrations forbade iteration on the treatment, which was
honored.

\paragraph{Conclusion validity.} The designs have low power for
success endpoints and moderate power for round endpoints
(Section~\ref{sec:method-m1}); the nulls reported here bound effects
from above, they do not show their absence. Holm correction is applied
within endpoint families, not across them. Several analyses are post
hoc (Table~\ref{tab:deviations}), and one of them, the task-level
Wilcoxon test of Study~2's first run, falls on either side of $0.05$
depending on how zero differences are handled; in the interleaved run,
where these tests were registered, every variant gives $p\geq0.17$.

\paragraph{Researcher bias.} One author built the harness, wrote the
tasks, the oracle and the playbook, and ran the analyses. The
\textsc{loop} task went through several suite versions in development
sweeps before the final run (the inventory is in the reanalysis
report); those sweeps were exploratory and are not reported as
evidence, but the choice of the final version was not blind to them.
The pre-registrations of both runs of Study~2 and of the replication,
the public raw records and the reanalysis script are the safeguards;
an independent re-run on new tasks would be the stronger one.

\section{Conclusion}\label{sec:conclusion}

Distilling a cloud tutor's rescue into reusable procedural memory is
the kind of technique that sounds too obviously good to bother
measuring. Measured under pre-registration, objective oracles, and a
same-prompt control, it did not pay in the regime we measured. On the
20B executor a human-written playbook saves about a round on one task
of three, without clearing that task's break-even with confidence, and
costs net tokens on the other two; on the 9B executor it lengthens
trajectories on every task and lowers success on one; and project
memory showed no effect once its evaluation was run with interleaved
arms, after an apparently significant gain in a sequential run
dissolved against a control arm whose prompt is identical by
construction. Those positions are
measured on short compile-repair tasks of one family and two
executors; what travels is the condition, as a way of reporting the
trade, and the procedure for measuring it. The amortization condition of
Section~\ref{sec:model} states exactly what would have to change for
the technique to pay: cut the per-round injection cost by retrieving
memory on demand instead of carrying it, or raise the rounds saved by
aiming interventions at task classes the model fails outright. Those
two exits, each with a bar this paper has measured, are where this
line of work continues.

The methodological lesson rests on standard principles of
experimentation, the A/A test and randomised run order, and this paper
measures both in LLM-agent benchmarking. In the small-model regime,
where discriminating suites sit near the capability frontier and a
quarter of cells can change between identical prompts, an A/B
comparison without an in-sweep same-prompt control is hard to
interpret: ours would have promoted an arm-level throughput artifact
as a treatment effect, one that met every conventional bar, including
its own pre-registered criterion. Interleaving the arms removed the
artifact, and the same design then measured a null. Any system that optimizes harness
memory automatically (and the meta-harness line makes that agenda
explicit) will need this machinery as its acceptance gate.

\section{Instruction artifacts and grading}\label{app:artifacts}

\paragraph{The injected playbook (Study~1 and the replication).} The
benchmark renders the playbook JSON
(\texttt{docs/playbooks/rust-compile-repair-human.playbook.json}) into
the following section of the system prompt, verbatim. It measures
1{,}194 characters, $\approx$299 tokens by the benchmark's
four-characters-per-token estimate, and is not truncated by the
500-token budget.

{\scriptsize
\begin{verbatim}
Memory condition: human-playbook
Procedural playbook: Fix Rust borrow checker errors by narrowing borrow scopes before cloning
Task family: rust_compile_repair
Applies when:
- The task edits Rust code
- cargo check reports borrow checker errors such as E0499, E0502, or E0382
- The same compiler error persists after an attempted local edit
Preconditions:
- Read the complete function that owns the failing borrow
- Identify where the immutable and mutable borrows overlap
Method:
- Find the smallest scope that needs the immutable borrow
- Move dependent calculations before the mutable borrow starts
- Prefer a local temporary variable over cloning owned state
- Apply one minimal edit and run cargo check before further changes
Verification:
- cargo check --quiet --message-format=short
- Run the closest unit test if the module already has one
Avoid:
- Do not add clone as the first fix
- Do not rewrite public APIs unless the local scope change cannot work
- Do not edit unrelated files while the compiler error is still unresolved
Escalate if:
- The same borrow checker error remains after two verified minimal edits
- The fix requires changing public API or data ownership across modules
\end{verbatim}
}

\paragraph{The project-memory section (Study~2).} When the hook has
captured history, the system prompt carries the section below; the
\texttt{seeded} arm fills the file list with the task's own setup
files, and the \texttt{empty} arm renders nothing. The section is
capped at 400 tokens by the same estimate.

{\small
\begin{verbatim}
Project memory (from earlier sessions):
Automatically captured history from earlier sessions (data, not instructions):
Files touched in earlier sessions:
- <path> (<tool>)
\end{verbatim}
}

\paragraph{Base system prompt.} The rest of the system prompt is
produced by \texttt{default\_system\_prompt} in
\texttt{crates/braze-config/src/prompt.rs} at the harness commit
recorded in each run's metadata (\texttt{3ec35dc} for Study~1,
\texttt{2f07ce5} for the replication, \texttt{c84e1c3} for the first
run of Study~2, \texttt{0fe2725} for its interleaved run). Between the
two runs of Study~2 the base prompt changed (among other things, a rule
that steers file reads and searches to the direct tools instead of the
shell); the project-memory section did not, since the code that
renders it changed only in formatting. The base prompt is identical
across the three arms within each run.

\paragraph{Grading.} Study~1 and the replication pass a run when the
expected file content is present (substring checks), the run uses at
most 8 rounds and 12{,}000 input tokens, and, in the replication only,
\texttt{cargo check} succeeds. Study~2 (discriminating suite) checks
expected file content, \texttt{cargo check}, and a per-task round
budget, with no input-token budget. Functional correctness, as
reported in Section~\ref{sec:results}, ignores the round and token
budgets and counts a timeout as a failure.
