Plan de desarrollo: modo aprendizaje para braze

Fecha: 2026-07-16 Estado: propuesta de arquitectura Nombre: learning mode / memoria procedimental destilada
Idea centralEl modelo local no aprende pesos: reutiliza playbooks destilados por un tutor cloud cuando hubo un fallo real.
Regla de seguridadTodo playbook nace como candidate; no se inyecta automaticamente hasta aprobarse o validarse.
MedicionLa prueba clave es multi-sesion: tarea A crea metodologia, tarea B mide transferencia local.
IntegracionReutiliza OpenRouterBackend, EscalatingBackend, braze-memory, hooks y braze-bench.

Tesis

El modo aprendizaje convierte una escalacion puntual a un modelo superior en una unidad reutilizable de memoria procedimental: un playbook estructurado, verificable, versionado y recuperable por el modelo local.

Cuando el modelo local falla, braze no solo consulta al modelo superior para resolver la tarea; le pide que explique que metodologia deberia haber seguido el modelo local, guarda esa metodologia como candidato y la valida antes de confiar en ella.

Principios

  1. Procedimientos, no notas libres.
  2. Off por default y siempre medible en braze-bench.
  3. Candidatos antes que verdad.
  4. Privacidad explicita antes de enviar contexto a OpenRouter.
  5. Retrieval antes de nueva escalacion.
  6. Validacion objetiva primero: tests, checks, schema validation o aserciones del bench.
  7. Token budget fijo y truncado por lineas completas.
  8. Sin auto-envenenamiento: el modelo local no escribe memoria confiable sobre si mismo.

Ciclo de vida

EstadoSignificadoInyeccion automatica

validatedAyudo en una tarea posterior con verificacion objetiva.Si

Flujo operacional

1. Tarea nueva

LearningRetriever busca playbooks relevantes por tags, extension de archivos, herramientas esperadas y texto de la tarea. Renderiza hasta N playbooks aprobados dentro de presupuesto y el modelo local intenta resolver.

2. Fallo local

LearningTrigger observa eventos tipados: schema failures repetidos, tool errors, max_turn_iterations, TurnBudgetExhausted, escalacion reactiva o fallo objetivo del bench.

3. Tutor cloud

Si la politica lo permite, LearningController envia un paquete redacted al tutor con objetivo, ultimos eventos relevantes, errores, checks y playbooks ya intentados. El tutor devuelve solucion inmediata y playbook JSON.

4. Persistencia

El JSON se valida contra schema. Si pasa, se guarda como candidate en .braze/playbooks/candidates/<id>.json. Si falla, solo queda evento de fallo.

5. Futuras tareas

Los playbooks aprobados se recuperan antes de escalar de nuevo. Si ayudan a una verificacion objetiva, suben su evidencia.

Plan por fases

Fase 0: congelar alcance

Documento de diseno, JSON Schema, politica de redaccion y metricas. Sin llamadas cloud ni inyeccion automatica.

Fase 1: store y renderer

Persistir playbooks manuales en braze-memory y renderizarlos dentro de presupuesto. Check: cargo test -p braze-memory.

Fase 2: retrieval e inyeccion controlada

Matching deterministico, wiring en CLI/bench y eventos PlaybookMatched/PlaybookInjected.

Fase 3: deteccion de fallos

Detectar triggers y construir paquetes redacted sin llamar todavia al tutor.

Fase 4: destilacion con OpenRouter

Prompt de tutor, parseo JSON estricto, validacion schema y guardado en candidates/.

Fase 5: CLI de revision

braze learn list/show/approve/retire/stats y movimiento atomico entre lifecycle directories.

Fase 6: bench multi-sesion

Comparar local, lead fallback, learning candidate, learning approved y human playbook.

Fase 7: promocion controlada

Auto-inyectar solo approved, validated y trusted, bajando confianza ante fallos.

Fase 8: export futuro

Exportar buenos playbooks a skills, dataset de fine-tuning y deduplicacion revisada.

Bench

BrazoDescripcion

learning-candidateEl tutor crea candidato, pero no se inyecta.
learning-approvedPlaybook aprobado se inyecta en tarea posterior.
human-playbookProcedimiento escrito manualmente como techo practico.

Metricas primarias: success rate local en tarea B, reduccion de leader_escalations, tokens totales, costo cloud y rondas hasta exito.

MVP recomendado:
  1. LearnedPlaybook + store + renderer.
  2. Inyeccion de playbooks manualmente aprobados.
  3. Deteccion de fallos sin tutor.
  4. Tutor OpenRouter que solo escribe candidate.
  5. CLI braze learn approve.
  6. Bench multi-sesion pequeno.

Pregunta de investigacion

Puede un harness local-first reducir escalaciones futuras destilando intervenciones cloud en memoria procedimental validada?

La pregunta mide transferencia procedimental, no solo fallback. Esa es la diferencia importante frente a "usar OpenRouter cuando falla".
