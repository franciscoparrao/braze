Auditoría completa de braze

Camino para convertirlo en el mejor software agéntico para modelos pequeños locales
2026-07-04 · commit 4ca193a · 12 crates · ~11k líneas Rust · 7 auditorías paralelas + literatura

El hallazgo transversal

El síntoma que motivó el proyecto —"los modelos pequeños no convergen y agotan las 20 iteraciones"— no es debilidad del modelo: es la tubería de contexto de braze borrándole el suelo bajo los pies. Cuatro auditores independientes convergieron en la misma cadena causal, y la literatura de 2026 la confirma. Ninguno de los cuatro eslabones es del modelo.

0 · Cómo se hizo esta auditoría

Se lanzaron siete auditorías independientes en paralelo, cada una con una lente distinta y sin ver el trabajo de las demás, más una revisión de literatura. Que hallazgos idénticos aparezcan en informes independientes es señal fuerte de que el problema es real y no un artefacto de una sola lectura.

1 · Resumen ejecutivo

braze es un MVP sólido y honesto: los contratos entre crates están bien diseñados, el diseño argv de las tools neutraliza la inyección de shell clásica, la carga diferida y el TTL de MCP están bien implementados, y la decisión de fondo —compactación diferencial determinística en vez de summarización con LLM— es exactamente la que la literatura de 2026 valida para modelos pequeños. El problema no es la arquitectura; son fallas de implementación concentradas en la tubería de contexto, más tres agujeros de seguridad puntuales.

La cadena causal de la no-convergencia

  1. Ollama trunca el contexto en silencio. braze-model nunca envía options.num_ctx, así que Ollama usa su default (2048–4096 tokens) y descarta el inicio del prompt sin error — lo primero que se pierde es el system prompt y las tools. B1 C3 F7
  2. La compactación borra el mensaje actual del usuario. Al cruzar el umbral, el prompt se construye con la ventana táctica vacía, reemplazada por un resumen que es puro conteo estadístico. A1 C1
  3. La compactación no es idempotente. Los eventos huérfanos nunca salen de la táctica → se re-dispara en cada ronda, apilando digests duplicados en O(n²). "Modo compactación permanente". A2 C2
  4. Sin tope de salida. max_tokens se ignora en Ollama → un loop de repetición genera sin límite, minutos de CPU. B2 F3

El resultado es un círculo vicioso: el modelo pierde contexto → repite tool calls → engorda el log → dispara más compactación → pierde más contexto. Arreglar esta tubería es la intervención de mayor impacto, y la mayoría son cambios pequeños y aditivos.

Las cinco cosas que hay que arreglar primero

  1. Configurar num_ctx + num_predict en Ollama — media hora, elimina la causa raíz #1.
  2. Preservar la cola viva de la ventana táctica al compactar — nunca descartar el mensaje del usuario ni el turno en curso.
  3. Hacer idempotente la compactación — un cursor en CompactionOccurred.
  4. Cerrar los tres agujeros de seguridad (glob -delete, RememberKey de shell, env en allowlist) — todos permiten hoy destrucción de datos sin confirmación.
  5. Arreglar el sandbox de braze-bench antes de correr el sweep — tal como está escribe en tu repo real y mide artefactos, no capacidad del modelo.

2 · Hallazgos críticos

La tubería de contexto

críticaB1 · Ollama no configura num_ctx → truncamiento silencioso
crates/braze-model/src/ollama_wire.rs:24-31,72-93

El body a /api/chat no lleva options. Ollama usa su default (2048–4096) y trunca el prompt del lado del servidor sin error. Con qwen2.5:3b, al tercer round el system prompt y las tools desaparecen y el modelo deja de converger. prompt_eval_count saturando sería la pista, pero nadie la compara.

struct OllamaOptions { num_ctx: u32, num_predict: i32, temperature: f32 }
// + si prompt_eval_count >= num_ctx - margen: warn! + compactar
G§4: aider exige num_ctx explícito y documenta el descarte silencioso; OpenHands exige ≥22000 "porque con 4096 ni siquiera cabe el system prompt".
críticaB2 · max_tokens se descarta en Ollama → loops sin tope
crates/braze-model/src/ollama_wire.rs:72-93

Anthropic honra max_tokens; Ollama lo ignora por completo (num_predict nunca se envía). Un llama3.2:1b en loop de repetición genera sin tope hasta el default del modelo — minutos de CPU quemada por turno. Fix: mapear req.max_tokens → options.num_predict.

críticaA1 / C1 · La compactación descarta la ventana táctica viva, incluido el mensaje del usuario
crates/braze-engine/src/engine.rs:399-417 + simple_compactor.rs:146-206

Con tactical.len() > 40, el prompt se construye con build_messages(&durable, &[]) — táctica vacía. El UserMessage recién apendeado es el evento más nuevo, así que se pliega en un resumen de conteos. El texto de la pregunta del usuario nunca llega al modelo.

let keep = KEEP_RAW_TAIL.min(tactical.len()); // 6-10
let (to_fold, live) = tactical.split_at(tactical.len() - keep);
let summary = self.compactor.compact_tactical(to_fold)?;
Ok(build_messages(&merge_summary(durable, summary), live))
críticaA2 / C2 · Compactación no idempotente → "modo permanente" O(n²)
crates/braze-session/src/simple_compactor.rs:68-83,111-144

Los huérfanos (UserMessage, AssistantText, Usage, ToolCallStarted) nunca salen de la táctica. Cruzado el umbral, la compactación se re-dispara en cada ronda, apila un CompactionOccurred nuevo cada vez, y el summary se vuelve decenas de digests casi idénticos enviados en cada request. Fix: contar solo eventos renderizables + CompactionOccurred { covers_up_to_index } (aditivo) que split use para descartar lo ya resumido; conservar solo el último summary.

críticaC3 · No existe presupuesto de tokens: se compacta por número de eventos
crates/braze-engine/src/engine.rs:23,399

El disparador es tactical.len() > 40 — un "ok" de 2 chars cuenta igual que un tool_result de 200 KB. La materia prima existe y se descarta: Usage.input_tokens se persiste pero nadie lo compara. Fix: disparador por presupuesto num_ctx - max_tokens - margen, calibrado con el usage real.

Seguridad

críticaD1 · Inyección de argv en glob: path="-delete" borra el cwd sin confirmación
crates/braze-tools-local/src/glob.rs:27-36

glob arma find <path> -type f -name <pattern>. Con path="-delete" → find -delete ... borra recursivamente el cwd. Y glob es un "read" que no pasa por el guard. Encadena con D6 (descripciones MCP sin sanitizar): un server malicioso puede instruir el glob path='-delete'. Fix: rechazar path que empiece con -; en grep, -- antes de posicionales.

críticaE1 · RememberKey de shell colisiona: rm -rf /tmp/x aprueba rm -rf /
crates/braze-permissions/src/guard.rs:35-42

La clave es solo (command[0], command[1]). Aprobar ["rm","-rf","/tmp/build"] recuerda Shell{rm,-rf}; un ["rm","-rf","/"] posterior → misma clave → se ejecuta sin preguntar. Igual con git push --force y bash -c "rm -rf /". Se agrava: se re-siembra en cada --resume. Fix: clave sobre el argv completo (argv_hash).

críticaE2 · env en el allowlist = bypass de ejecución arbitraria
crates/braze-permissions/src/classifier.rs:128

env figura como read-only seguro, pero env rm -rf /tmp/x ejecuta el rm → Reversible → sin prompt. Cualquier destructivo prefijado con env (o bash -c) esquiva la capa 2. Fix: quitar env del allowlist + test adversarial.

críticaE3 · Decisiones de permiso re-sembradas en --resume sin validar integridad
crates/braze-cli/src/main.rs:162-176

El replay siembra PermissionDecided{allowed:true} del log sin checksum. Si HOME/XDG no están, session_dir cae dentro del cwd — donde el propio modelo puede write_file (reversible, sin prompt) sobre el log y auto-aprobarse acciones irreversibles. Combinado con E1, cada entrada concede más de lo aprobado. Fix: validar el log + session_dir fuera del cwd.

Corrección del historial (corrupción permanente)

críticaA3 / B4 · El stream no tiene canal de error: texto truncado se persiste como respuesta final
crates/braze-engine/src/engine.rs:122-148 + anthropic.rs / ollama.rs

CompletionEvent no es Result. Ante corte de red o JSON malformado, los backends loguean y terminan el stream en silencio; el engine no distingue "llegó Done" de "murió" y persiste el parcial. Un evento SSE error de Anthropic (overloaded_error) se convierte en Done — indistinguible de éxito, sin retry. Fix: Stream<Item=Result<CompletionEvent>> + saw_done en el engine.

críticaA4 · Completion tardía post-timeout duplica ToolCallCompleted → 400 permanente
crates/braze-engine/src/engine.rs:342-378

El canal mpsc es compartido entre rondas. Un task que hizo timeout, al completar, entrega su resultado a la ronda siguiente; con el handle ajeno se rescata el id viejo → segundo tool_result para el mismo tool_use_id → Anthropic responde 400 y todos los turnos siguientes quedan rotos (log append-only). Fix: descartar completions cuyo handle no esté en pending.

críticaC4 · tool_use huérfano tras crash envenena el resume con 400 permanente
crates/braze-engine/src/engine.rs:209-336 + simple_compactor.rs:81

run_turn persiste AssistantToolCall antes de despachar. Si el proceso muere antes del resultado, el log queda con un tool_use sin tool_result; al resumir contra Anthropic cada turno falla con 400. Peor: is_settled_durable lo migra a durable sin verificar el par. Fix: reparación al cargar (sintetizar ToolCallCompleted{is_error:true} por cada huérfano).

El harness de evaluación (invalida el sweep pendiente)

críticaF1 · El sandbox no es el cwd de las tools: aislamiento roto, tareas irresolubles, escritura en el repo real
crates/braze-bench/src/runner.rs:56-59 + braze-tools-local/*

El sandbox solo alimenta el allowlist. Ninguna tool resuelve rutas contra él (shell_exec sin .current_dir()). Resultado: read_file_basic es irresoluble (solo "pasa" si el modelo alucina el "3"); write_file_basic escribe en tu repo real; glob/grep/shell operan sobre el workspace braze real. Fix: inyectar workdir, resolver rutas, .current_dir(), comunicarlo en el system prompt.

críticaF3 · N=1 por celda, sin temperature ni seed → la tabla es ruido
crates/braze-bench/src/main.rs:29-40

Cada (tarea, backend) corre una vez con T≈0.8. Para 1B-7B, 5/7 vs 4/7 con N=1 no distingue nada. Fix: --repetitions N (≥5), temperature:0.0, seed:42, intervalos de Wilson.

críticaF2 · Sin timeout por tarea ni presupuesto del sweep
crates/braze-bench/src/runner.rs:81-86

run_turn se awaitea sin timeout; la única cota es 20 rondas (no tiempo). Con >20 min por tarea no-convergente, un sweep 7×4 quema horas. Fix: timeout_secs por tarea + causa estructurada.

Implicación operativa: F1+F2+F3 juntos significan que el sweep completo pendiente no debe correrse hasta arreglar el bench. Los números actuales medirían artefactos del harness más ruido de N=1, no capacidad de los modelos.

3 · Hallazgos altos

14 hallazgos. Los de mayor impacto para modelos pequeños:

altaA5 · Cero detección de loops/repetición

Nada detecta que el modelo pidió la misma tool con los mismos args — el patrón dominante de no-convergencia en 1B. Fix: HashSet<(name,args)> por turno + nudge sintético en repetición exacta.

G§5: fingerprint (tool, args) con umbral 3 supera a los caps genéricos; ~12% de repetición degenerada observada.
altaA6 · El cap corta en seco y en chat el ? mata el REPL

Agotar las 20 iteraciones devuelve Err; en Command::Chat el ? mata el proceso entero. Un 429 transitorio también. Fix: ronda final sin tools + match/continue en el CLI.

altaA7 · Tool alucinada se despacha; el error no lista las tools válidas

El modelo recibe "tool not found: read_files" sin pista. Un 1B repetirá. Fix: nudge con los nombres disponibles + sugerencia por distancia de edición.

altaB5 · Sin fallback de tool calls emitidos como texto JSON

Modelos que emiten {"name":...} en content (o gemma3 sin soporte de tools) matan el loop en el primer paso. Fix: rescatar el JSON del texto; para gemma3, reintentar sin tools.

G§1: "la mitad de los fallos de modelos chicos son de parser, no del modelo".
altaD2 · Cero truncamiento de outputs de tools

Un read_file de 300 KB o grep -r sobre .git/target desborda la ventana y dispara B1. Fix: tope por bytes/líneas con cola accionable, configurable por modelo.

altaD3 · Carga diferida de una vía: el schema real solo llega como castigo

El modelo ve {additionalProperties:true}; el schema real solo aparece tras fallar validación (un round-trip perdido, minutos en CPU). Fix: schema real de entrada para las 6 tools locales; stubs diferidos solo para MCP.

Ver los 8 hallazgos altos restantes (A8, B6, C5, C6, C7, D4, F4–F8)
  • altaA8 · Un provider MCP que muere brickea todos los turnos (fail-fast de all_stubs). Fix: all_stubs_lossy().
  • altaB6 · stop_reason/done_reason ignorados → truncamiento por max_tokens indetectable; el tool call se dropea en silencio.
  • altaC5 · Una línea JSONL parcial hace fallar load() completo. Fix: tolerar la última línea + sync_data.
  • altaC6 · El resumen de compactación es un conteo sin semántica. Fix: digest extractivo determinístico (user messages, tools tocadas, errores).
  • altaC7 · durable_events crece sin límite; los arguments de write_file (cuerpo del archivo) viven en el prompt para siempre. Fix: limpiar argumentos + tope de pares durables.
  • altaD4 · dispatch del registry anula el TTL de MCP forzando refetch en servers que no poseen la tool.
  • altaF4 · Verificación por proxy (nombre de tool) en vez de resultado — pasa con la tool fallida. Fix: aserciones de outcome sobre el sandbox.
  • altaF5 · Sin taxonomía de causa de fallo; los fallos del harness se omiten de la tabla (denominadores distintos por backend).
  • altaF6 · No se mide el número de rondas — la métrica diagnóstica central. El engine ya persiste un Usage por ronda.
  • altaF7 · El bench no fija num_ctx → mide un artefacto del harness, no el modelo.
  • altaF8 · La suite no tiene gradiente de dificultad; sin multi-step no ve el techo real (BFCL: single OK, multi-turn colapsa bajo 4B).

4 · Hallazgos medios y bajos

16 medios + 13 bajos. Todos reales y accionables; menor impacto o probabilidad. Detalle completo en el Markdown.

Medios — observabilidad, seguridad secundaria, robustez
  • A9 · Observabilidad insuficiente: sin spans por turno/ronda/tool-call ni traza al compactar.
  • A10 · System prompt fijo de una línea, sin reglas anti-loop ni few-shot — la palanca más barata, sin usar. (G§1: few-shot +21.5%, CoT breve gana.)
  • A11 · Respuesta final vacía tratada como éxito silencioso.
  • D5 · Sin namespacing de tools MCP: colisión read_file local vs MCP → 400.
  • D6 · Descripciones MCP entran al prompt sin sanitizar (secuestro por descripción).
  • D7 · Reads sin gate leen ~/.ssh/id_rsa; con D6, exfiltración al contexto.
  • D8 · shell_exec sin timeout propio; procesos huérfanos nunca matados.
  • E5 · El prompt de permiso no muestra cwd, ruta resuelta ni motivo.
  • E6 · API key con derive(Debug, Serialize) sin redacción.
  • B7 · Sin timeouts HTTP (connect + read-idle, no total).
  • B8 · 429 sin retry-after ni backoff; 529 tratado como permanente.
  • B9 · Ollama sin keep_alive → recarga del modelo entre turnos.
  • B10 · tool_results sin tool_name → con 2+ calls, un 3B no sabe cuál es cuál.
  • B11 · Sin temperature en ningún backend.
  • C8–C11 · CompactionOccurred intra-ventana invisible; sin versionado de formato; ventana/umbral hardcodeados; re-split O(n²) del log por ronda.
  • F9–F11 · Arranque en frío contamina medias; expect_text_contains frágil; denegaciones contadas como fallo de ejecución.
Bajos — consistencia, mensajes de error, deuda menor
  • A12–A15 · estimate_dropped_tokens usa Debug repr; IDs de Ollama con contador global; timeout por next_completed no por ronda; tests faltantes del loop.
  • D9–D12 · shell_exec argv-only hostil para 1-3B; read_file sobre binario críptico; estampida de caché MCP; tests ausentes de argv-injection.
  • B12–B16 · Sin prompt caching; token accounting incompleto; arguments string JSON no manejado; cancelación sin API; fixtures no reales.
  • C12–C16 · Dup de A12; timeout con id vacío → 400; flush sin sync_data; mezcla de idiomas; cero tests del disparador de compactación.
  • E7–E8 · Tests adversariales faltantes; Mutex envenenado (fail-closed).
  • F12–F14 · Referencias muertas en PLAN.md; fuga de dir de sesión; confounder de idioma.

5 · Fortalezas (no tocar)

✓ argv, no sh -c ✓ tools locales ejemplares para 1-3B ✓ MutexGuard nunca cruza .await ✓ parser SSE robusto ✓ API nativa de Ollama ✓ invariante de no-pérdida del split ✓ event sourcing limpio ✓ TTL de MCP bien testeado ✓ default-deny real ✓ bench mide el motor real
  • Diseño argv de las tools: neutraliza ;, &&, |, subshells, $(). La decisión de seguridad más importante, y se sostiene (E1/E2 son reentradas puntuales).
  • Las 6 tools locales: nombres cortos, schemas 100% planos, defaults sensatos, errores accionables en edit_file — justo lo que G§3 recomienda.
  • La compactación diferencial determinística es la dirección que la literatura 2026 valida (G§4): la summarización con un 3B es cara y mala. El problema de C6 es qué extrae (nada), no la estrategia.

6 · Estado del arte (julio 2026) y validación externa

Techo honesto: 1-4B logran 90%+ de tool calls válidas single-turn con buen harness, pero el multi-turn complejo colapsa (BFCL: Qwen3-1.7B 17% multi-turn; ComplexFuncBench <10B ≤8.4%). La conclusión estratégica: mover la planificación al harness, no hacer que el 3B planifique mejor. Es exactamente la tesis de braze.

8 · Sobre el sweep pendiente

El estado de sesión traía como pendiente "correr el sweep completo contra los 4 backends". La auditoría concluye que ese sweep no debe correrse todavía: por F1 el harness escribiría en el repo real y mediría el cwd equivocado, por F7/B1 mediría el truncamiento de num_ctx en vez de capacidad, y por F3 N=1 con T=0.8 daría ruido. El orden correcto es Grupo E → luego el sweep. Arreglado el bench, el sweep no solo será válido sino que servirá como test de regresión de los Grupos A–D.
