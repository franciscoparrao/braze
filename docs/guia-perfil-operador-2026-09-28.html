Perfeccionar el harness usándolo

Trece ejercicios en progresión, del que no puede romper nada al que compara braze con Claude Code en una tarea real. Cada uno prueba una pieza del harness, dice qué esperar y qué palanca tocar cuando falla. La idea es que cada fricción termine en un ajuste de la política, de la config, de una skill o del código, no en un rodeo.

La referencia de comandos y archivos está al final. El binario que ejecuta todo esto es ~/.cargo/bin/braze, reinstalado hoy con el prompt que nombra el modelo, el scrubber de secretos y el "siempre" acotado.

Método

Cada ejercicio tiene la misma forma: haz (el comando), espera (lo que un harness sano produce), si falla (la palanca: qué archivo o pieza ajusta ese comportamiento) y reporta (lo que necesito para reproducirlo). Anota siempre el session id que braze imprime al arrancar; el rollout completo queda en ~/.local/share/braze/sessions/<id>.jsonl.

Regla de oro mientras pruebas: cuando aparezca un prompt de permiso con un bash -lc … largo que no entiendes, responde n. El modelo tiene tools directas para leer, buscar y editar; si insiste en scripts, eso es un hallazgo sobre el prompt, no algo que aprobar.

Primer hallazgo real ya corregido: preguntado "¿qué modelo eres?", el modelo volcó env al contexto y un token viajó al proveedor. Ahora el prompt nombra el modelo, los tool results redactan valores que parecen credenciales, y "siempre" sobre un bash -c aprueba solo ese comando exacto. Rota el token de Zenodo si no lo hiciste.

Primera pasada ya corrida (2026-09-29, por el asistente sobre clones): 10 de 13 ejercicios en verde, tres hallazgos convertidos en arreglos (DSML de DeepSeek en el rescate, scripts propios en la política, observaciones completas configurables). Tabla, session ids y hallazgos en docs/tutorial-resultados-2026-09-29.md. Vale la pena que repitas los ejercicios 2, 5, 6 y 11 con el binario nuevo: son los que dependen del modelo.

Las palancas, de más barata a más cara: policy.toml (qué corre sin preguntar), config.json (modelo, skills, hooks, topes), el SKILL.md de una skill, el system prompt (crates/braze-config/src/prompt.rs) y el resto del código. Antes de subir de nivel, agota el anterior.

AOrientación

Riesgo cero: solo lectura. Prueban el prompt, las tools de lectura y los hooks de contexto.

1Quién eres

Haz
cd ~/proyectos/<cualquiera> && braze run "¿Qué modelo eres y quién te ejecuta?"
Espera
Una ronda, cero tools, y el nombre deepseek-v4.1-flash sacado de su propio prompt.
Si falla
Si vuelve a usar tools para averiguarlo, la línea del prompt no está llegando: revisa que which braze sea ~/.cargo/bin/braze con fecha de hoy. Si es el binario correcto, es un problema de obediencia del modelo: prueba el mismo comando con --model qwen3.8-flash.
Reporta
La salida completa y el session id. Es el ejercicio más barato y el que más dice sobre el modelo.

2Leer un repo

Haz
cd ~/proyectos/<repo real que no sea braze>
braze chat --tui
> Explícame la estructura de este repositorio en diez líneas: qué hace, dónde está el punto de entrada y dónde los tests.
Espera
glob, read_file y grep, entre 3 y 8 rondas, ninguna pregunta de permiso, y una respuesta que nombre archivos reales.
Si falla

Pide permiso para bash -lc find … o cat: responde n y observa si se corrige usando las tools. Si no se corrige, es un hallazgo de prompt: anota el comando exacto que pidió.

Más de 10 rondas o se pierde: mira el rollout; si repite lecturas, es el colapso de observaciones (tactical_window).

Reporta
Rondas, si pidió permisos y cuáles, y si el resumen era correcto.

3Contexto de sesión

Haz
cd ~/proyectos/<proyecto con session_state>
braze run "Sin usar herramientas: ¿cuál es la tarea actual del proyecto y qué quedó pendiente?"
Espera
La respuesta cita tu resume de context_manager.py y el MEMORY.md del proyecto, en una ronda.
Si falla

No sabe nada: comprueba que el directorio tenga slug exacto con python3 ~/.claude/session_state/context_manager.py detect --dir $PWD --exact. El hook detecta por ruta exacta, no por ancestro.

Sabe pero mezcla proyectos: el MEMORY.md se busca por la ruta del cwd transformada; revisa ~/.claude/projects/.

Palanca: hooks.session_start en config.json; trazas con RUST_LOG=braze=info.

Reporta
El slug detectado y la respuesta.

BSkills

Prueban el discovery, los argumentos, el presupuesto de cuerpo y, sobre todo, cuánto sigue un modelo de Go una skill escrita para Claude. Este es el riesgo real del plan.

4Skill de guía pura

Haz
braze run '/destelegrafiar check <un-documento-tuyo.md>'
Espera
La tabla de hallazgos con los patrones de la skill, leyendo el archivo con read_file. Compara con lo que te da Claude Code sobre el mismo archivo.
Si falla

"Skill no encontrada": braze chat --tui, /skills, y busca el nombre; si no está, su SKILL.md no tiene name: o description:.

Se carga pero ignora las instrucciones: mira en el rollout skill_loaded … truncated; si es true, sube skills.max_body_tokens. Si no, es fidelidad del modelo: repite con --model qwen3.8-flash y anota la diferencia.

Reporta
El nombre de la skill, si cargó, y en qué se apartó del comportamiento en Claude Code.

5Skill con script

Haz
braze run '$memoria status'
Espera
Corre los scripts de la skill con python3 sin preguntar (regla dev-toolchain), lee ~/.claude/session_state y ~/vault sin preguntar (references), y entrega el estado en menos de 10 rondas.
Si falla

"read path denied" fuera del proyecto: falta esa ruta en references de config.json.

Deniega un comando: sin terminal todo confirm es no. Repite en braze chat --tui y responde a a lo que sea legítimo; luego confirma con braze permissions policy que la regla quedó.

Muchas rondas y tokens: anota cuáles comandos pidió que fueron denegados; son candidatos a la política.

Reporta
Rondas, tokens de entrada (los imprime --output-format json) y los comandos denegados.

6Skill que pide subagentes

Haz
braze run '/tex-review --quick <un-manuscrito.tex>'
Espera
Braze no tiene subagente genérico. Un buen desenlace es que el modelo diga que no dispone de Agent y haga la revisión él mismo, en secuencia, con las herramientas que sí tiene. Un mal desenlace es que invente que lanzó agentes.
Si falla
Es el ejercicio que decide si construir el subagente genérico. Si la revisión secuencial te sirve, no hace falta; si no, es el siguiente punto del roadmap.
Reporta
Qué hizo en lugar de los subagentes y si el resultado era usable.

CEditar y verificar

Escritura dentro del proyecto: edit_file, el check post-edición y la política de herramientas. Hazlo en una rama.

7Cambio acotado con tests

Haz
cd ~/proyectos/<repo con tests> && git switch -c prueba-braze
braze chat --tui
> Renombra la función <X> a <Y> en todo el proyecto y corre los tests. Dime qué cambiaste.
Espera
grep para localizar, edit_file por archivo, cargo test o pytest sin preguntar, y un resumen honesto del resultado de los tests. En Rust, el check post-edición le devuelve los errores de compilación en el mismo tool result.
Si falla

Usa write_file reescribiendo archivos enteros: es una preferencia conocida de modelos chicos; anótalo. Si además pierde contenido, es grave: reporta con el diff.

Pide permiso para el runner de tests: agrégalo a dev-toolchain en policy.toml o responde a.

Palancas: formatters en config para el check post-edición en otros lenguajes; disable_syntactic_edit_gate si el gate rechaza ediciones válidas.

Reporta
El git diff resultante y si los tests corrieron de verdad (el rollout lo muestra).

8Fallo honesto

Haz
Pide algo que va a fallar de forma segura: 
> Corre los tests con el comando `pytest --nope` y dime el resultado.
Espera
Reporta el error tal cual, sin inventar que pasó. Si la política deniega el comando, debe decir que no corrió y darte el comando para que lo corras tú.
Si falla
Fabrica éxito: es el peor modo de fallo y depende del modelo. Repite con otro modelo de Go y anota cuál lo hace bien. Palanca de código: el mensaje de denegación en braze-tools-local.
Reporta
La frase exacta con la que reportó el fallo.

Prueban el policy engine, la respuesta "siempre" y las tools web con hosts permitidos.

9Confirmar, negar, siempre

Haz
braze chat
> Ejecuta con shell_exec exactamente: tree -L 1     (o cualquier programa que no esté en la política)
Espera
El prompt [y = sí / N = no / a = siempre]. Responde n y mira que el modelo lo reporte sin insistir. Vuelve a pedirlo, responde a, y comprueba: 
braze permissions policy      # debe listar always-shell-tree
braze permissions suggest     # propone reglas desde tus sesiones
Si falla
Con a no aparece la regla: mira si el mensaje dijo "no se pudo guardar"; la política se valida antes de escribir y un archivo inválido lo impide. Si la regla es más amplia de lo que quieres, edítala a mano: primera regla que matchea gana, así que un deny arriba manda.
Reporta
La regla que quedó escrita y si te pareció bien generalizada.

10Web con política

Haz
braze run "Busca en la web cómo se usa <una función de una librería que uses> y resume con un ejemplo, citando la URL."
Espera
web_search y luego web_fetch a un host de la lista permitida, sin preguntar; resumen con la URL real.
Si falla

"no results parsed": DuckDuckGo cambió el markup o devolvió un bot-check; reporta y de momento dale la URL directa.

Pregunta por un host: si es uno que usas seguido, a en la TUI o agrégalo a web-allowed-hosts. Si quieres todo abierto, match = ["*"], aceptando el riesgo de exfiltración por URL.

Reporta
La consulta, los hosts que pidió y si el resumen correspondía a la página.

ESesiones largas

Compactación, refresco de contexto y reanudación: lo que decide si braze sirve para una tarde entera y no para cinco minutos.

11Compactar y reanudar

Haz
Una tarea que pida muchas lecturas (más de 40 eventos): "lee los diez archivos de src/ y haz un mapa de dependencias". Luego cierra con /quit y reanuda: 
braze chat --resume <session id>
> ¿En qué quedamos y qué falta?
Espera
En el rollout aparecen compaction_occurred y, con RUST_LOG=braze=info, "session context refrescado tras compactación". Al reanudar, recuerda la tarea y no vuelve a pedir permisos ya aprobados.
Si falla
Pierde el hilo tras compactar: el resumen es extractivo por default. Palancas: tactical_compaction_threshold más alto, o enable_lead_summary para que un modelo redacte el resumen. Si pierde justamente una restricción que le diste ("no toques X"), es la ruta SC: decláralas al inicio como constraints.
Reporta
El session id y qué olvidó.

12Cambiar de modelo

Haz
En la TUI, a mitad de una sesión: 
/model zen:qwen3.8-flash
y repite la última petición.
Espera
El cambio es inmediato y conserva la conversación. qwen fue el segundo del sweep: parecido en aciertos, más lento.
Si falla
Un modelo de Go rechaza un parámetro: braze ya degrada seed; kimi-k2.7-code exige temperatura 1 y no sirve con el default. Otros errores 400 de Go son reporte directo.
Reporta
Cuál modelo hizo mejor la misma tarea, con rondas y tiempo.

FComparación

13Misma tarea, dos harness

Haz
Toma una tarea real de tu día, de las que le darías a Claude Code, y dásela primero a braze y después a Claude Code, con el mismo texto.
Espera
No espero paridad. Espero saber dónde está la brecha: en el modelo (deepseek vs Claude), en las tools que faltan (subagentes, LSP) o en el harness (permisos, contexto, skills).
Si falla
Este ejercicio no falla: produce el dato que ordena el roadmap. Cada brecha atribuible al harness es un punto a construir; las atribuibles al modelo se miden con el bench antes de tocar código.
Reporta
La tarea, los dos resultados y tu veredicto en una frase. Con tres de estos ya tenemos el siguiente sprint.
