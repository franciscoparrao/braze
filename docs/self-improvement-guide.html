Auto-mejora supervisada

Que braze edite su propio motor — en un worktree descartable, con vos aprobando cada escritura antes de que ocurra.

commit de referencia: 9f21eb3 proyecto: /home/franciscoparrao/proyectos/braze ver también: docs/usability-testing-guide.html, docs/self-improvement-exercises.md

La forma más honesta de probar si braze sirve para desarrollo real es dejarlo trabajar sobre su propio código — no un sandbox sintético del bench, el motor de verdad. Eso es más delicado que cualquier tarea del bench: un mal diff acá no rompe una tarea de prueba, rompe la herramienta. Esta guía documenta el modo pensado específicamente para ese riesgo: --supervised más un worktree aislado, de forma que nada llega a main sin que lo hayas visto venir, paso a paso.

1Qué es --supervised

Hoy, si braze corre parado dentro de su propio repo, cualquier write_file/edit_file ahí se clasifica Reversible (cae dentro del WorkdirAllowlist) — no pide confirmación, se aplica directo. Eso tiene sentido para un proyecto cualquiera del usuario, pero no para una sesión donde el "proyecto" es el motor que está ejecutando la sesión.

--supervised reemplaza el clasificador por uno que marca todo como Irreversible (AlwaysIrreversibleClassifier, crates/braze-permissions/src/classifier.rs) — así que cada acción, sin excepción, pasa por el mismo overlay de aprobación (y/n) que hoy solo ven las acciones genuinamente irreversibles.

braze chat --tui --supervised --backend anthropic --model claude-opus-4-6-20260805

Funciona en chat y en run, con o sin --tui (el loop de texto plano también tiene confirmación interactiva por stdin). Sin --tui, cada aprobación es una pregunta y/n bloqueante en la terminal — perfectamente usable para esto, aunque el overlay de la TUI se lee más cómodo.

2Flujo paso a paso

1

Crear un worktree nuevo, en una rama descartable — nunca el checkout activo, nunca main. Si algo sale mal, se tira el worktree entero y no pasó nada.

cd ~/proyectos/braze
git worktree add ../braze-self-improve-si1 -b self-improve/si-1
cd ../braze-self-improve-si1
2

Arrancar braze parado en ese worktree, en modo supervisado, contra un backend capaz (esto es código real, no una tarea de bench — recomendado Anthropic o openrouter:deepseek/deepseek-v4-flash, no el Qwen local todavía).

braze chat --tui --supervised --backend anthropic --model claude-opus-4-6-20260805
3

Pegar el prompt de un ejercicio de docs/self-improvement-exercises.md (sección 3, abajo).

4

Aprobar o denegar cada acción a medida que aparece — ver la sección 4 para qué mirar en cada una. Denegar no aborta la sesión: braze ve la denegación y puede intentar otra cosa.

5

Al terminar, verificar en el worktree (el guardrail de post_edit_check ya corrió cargo check después de cada edición, pero conviene la pasada completa):

cargo build --workspace && cargo test --workspace && cargo clippy --workspace --all-targets -- -D warnings
6

Revisar el diff completo con calma (git diff main). Si convence: git push -u origin self-improve/si-1 y un PR normal. Si no: cd ~/proyectos/braze && git worktree remove ../braze-self-improve-si1 --force y listo, sin rastro.

Antes de arrancar

--supervised te protege de una escritura que no viste venir, no de aprobar algo que en el momento parecía razonable pero no lo era. La revisión del paso 6 sigue siendo necesaria — el modo supervisado baja el riesgo de sorpresa, no reemplaza la revisión de código.

4Qué vigilar al aprobar

  • Alcance del archivo: ¿la edición toca solo lo que el ejercicio pidió, o se metió a "mejorar" algo no pedido de paso?
  • Tests nuevos, no solo código nuevo: si agrega una función pero no un test que la ejercite, es una señal de alerta — la convención del proyecto es "cada incremento se prueba".
  • Comandos de shell: bajo --supervised hasta ls pide confirmación — no te acostumbres a aprobar por reflejo; seguí leyendo el comando exacto cada vez.
  • Un "no" no es un fracaso: si algo no se ve bien a mitad de camino, denegar y dejar que el modelo reaccione es información útil — anotalo como si fuera un hallazgo de usabilidad más.

5Cuándo no usar esto

--supervised es fricción a propósito — no es el modo para una sesión normal de braze chat sobre un proyecto cualquiera (ahí el clasificador por defecto ya distingue bien qué pedir y qué no). Tiene sentido específicamente para: braze editando su propio código fuente, o cualquier otra sesión de alto riesgo donde preferís ver cada paso aunque sea más lento.

Complementa docs/usability-testing-guide.html (probar braze como usuario) — acá el foco es distinto: no es encontrar fricción de uso, es dejar que braze *modifique su propio motor* con la menor sorpresa posible.
